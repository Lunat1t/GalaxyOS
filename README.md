# Galaxy 1.7 — Verified Flow

Локальный конвейер задач с восемью ИИ-ролями, Obsidian-заметками, SQLite-памятью и MCP. Релиз 1.7 исправляет обработку результатов, передачу контекста, очередь и порядок проверки перед завершением.

Это проверяемый прототип для доверенного локального рабочего каталога. Реальная интеллектуальная работа требует установленного и авторизованного CLI-провайдера. Автоматическая OS-изоляция и облачная синхронизация не реализованы.

## Быстрый запуск

Нужны Python 3.10+, Node.js 18+ и Git для операций с репозиторием. Сторонние Python-пакеты не требуются. Проверенная среда сборки: Linux, Python 3.12, Node.js 24, Git 2.51. Windows-ветки кода присутствуют, но в этом релизе не проверялись.

Из папки `galaxy-v1.7`:

```bash
python run_tests.py
python solar.py --version
python solar.py list
python solar.py verify TASK-002
python solar.py audit
```

`TASK-002` проверяет калькулятор. `verify` запускает проверку; `run` управляет классическим детерминированным workflow. Эти команды не доказывают способность модели решать новые задачи.

## Запуск ИИ-конвейера

```bash
python solar.py agents
python solar.py agent-run TASK-002 --provider codex
```

Доступны адаптеры `codex exec --skip-git-repo-check` и `agy -p`. Флаг Codex нужен, потому что Galaxy может поставляться как проверенный каталог без `.git`; он не отключает sandbox или подтверждения действий. Адаптеры используют локальную конфигурацию, авторизацию и ограничения установленного CLI. Galaxy не отключает ограничения провайдера и не устанавливает его автоматически. Готовность и формат вывода конкретной версии провайдера необходимо проверить на реальном запуске. Подключение MCP-конфигурации выполняется отдельно в используемом клиенте.

При отсутствии CLI задача блокируется. В релизных тестах используются явно обозначенные FakeAgent и внешний тестовый исполняемый файл; живые Codex/Antigravity не тестировались.

Обычный маршрут направляется полем `next_agent`. Для диагностики:

```bash
python solar.py agent-run TASK-002 --provider codex --route Sun,Earth,Moon,Mercury
```

Все шаги идут через реальные очереди `WorkerMesh`. Один маршрут выполняет зависимые шаги последовательно. Автоматического параллельного разветвления одного задания в 1.7 нет. Независимые обработчики разных очередей умеют работать одновременно, что проверяется тестами. На рабочий каталог установлен общий lock: два процесса Galaxy не должны одновременно менять одну кодовую базу.

## Интерактивный чат с ядром (REPL)

В версии 1.7.1 доступен интерактивный диалоговый интерфейс для прямого общения с ядром и планетами через CLI провайдеры `codex` или `antigravity` (`agy`):

```bash
# Быстрый запуск чата (по умолчанию: codex):
python solar.py chat

# Запуск с провайдером Antigravity и начальной ролью Sun:
python solar.py chat --provider antigravity --role Sun

# Обсуждение конкретной задачи с подгрузкой её контекста и рантайм-следов:
python solar.py chat --task TASK-002

# Или напрямую через скрипт:
python chat.py --provider antigravity --role Earth
```

Внутри чата доступны команды:
- `/role <NAME>` — сменить планетарную персону (`Sun`, `Venera`, `Mars`, `Ceres`, `Earth`, `Neptun`, `Moon`, `Mercury`, или `none`).
- `/provider <NAME>` — переключить провайдер между `codex` и `antigravity`.
- `/task <TASK-ID>` — привязать контекст задачи (спецификацию и историю запусков).
- `/memory <QUERY>` — поиск в локальной базе памяти Galaxy (`memory/index.db`).
- `/save [PATH]` — сохранить лог диалога в Markdown.
- `/clear` — очистить текущую историю.
- `/help`, `/exit`, `/quit`.

## Контракт результата

```json
{
  "status": "PASS",
  "summary": "Исправлено округление; выбран Decimal для денежных величин.",
  "next_agent": "Moon",
  "artifacts": ["src/calculator.py"],
  "evidence": ["python -m unittest: 12 tests passed"]
}
```

Допустимые модельные статусы: `PASS`, `FAIL`, `BLOCKED`. Нулевой exit code CLI не подменяет статус модели. Отсутствующий, неоднозначный или неправильный JSON даёт `INVALID_RESULT`. stderr сохраняется отдельно и не разбирается как ответ модели.

`summary`, `artifacts`, `evidence` передаются следующей роли. Заявленные файлы проверяются и сохраняются до удаления временной копии. Следующие аналитические роли получают эти сохранённые файлы в своих копиях. Артефакт должен быть относительным обычным файлом внутри проекта, до 10 MiB.

Moon может вернуть `FAIL` и `next_agent: Earth` для исправления. Число повторов ограничено. Ошибка остаётся ошибкой в истории.

## Проверка и Git

Перед Mercury обязательно выполняется исходный `verify_command` в отдельной копии. Проверка должна завершиться с кодом 0 и не менять исходные файлы. Сохраняются hash набора файлов, HEAD, команда, stdout/stderr и run_id.

Существующие файлы в `tests/`, файлы `test_*`, `*.test.js`, `*.test.py` и файлы, непосредственно указанные аргументами `verify_command`, фиксируются в начале запуска. Изменение этих проверок требует отдельного осознанного пересмотра, а не автоматического принятия в том же запуске. Это не доказательство полноты тестов и не защита от недоверенного нативного процесса.

Mercury работает в временной копии и только составляет итог. Git-коммит выполняется отдельной явной командой:

```bash
python solar.py finalize TASK-002 --run RUN_ID --message "Fix calculator"
```

Команда принимает только DONE-запуск с неизменёнными после QA файлами и HEAD. Индекс должен быть пуст, начальный коммит должен существовать. В коммит включаются только изменённые этим запуском файлы, включая новые. Содержимое Git index сверяется с проверенными байтами; преобразования Git filters/line endings, меняющие эти байты, приводят к отказу. Если эти файлы были изменены ещё до запуска, финализация откажет. Git hooks на этой операции отключены, чтобы они не заменили проверенное содержимое. Отправки в remote нет. После неудачной операции staging может остаться в индексе — проверьте `git status`.

## Состояние и восстановление

Каждый запуск имеет `run_id`. SQLite `traces/runtime.db` — источник истины. Состояние шага, ACK и следующее сообщение записываются одной транзакцией. JSON и frontmatter задачи — восстанавливаемые представления состояния.

```bash
python solar.py agent-run TASK-002 --resume RUN_ID
python solar.py runtime-history --task TASK-002
python solar.py runtime-status
```

Доказательства: `tasks/task-002/runs/RUN_ID/`; указатель: `tasks/task-002/latest-run.json`.

После сбоя между завершёнными шагами маршрут продолжается с checkpoint. Если процесс погиб во время работы провайдера, неизвестно, какие внешние действия он успел сделать. Такой запуск получает `INTERRUPTED`; проверьте изменения и начните новый запуск. Автоматического повторения сомнительных побочных действий нет. Старый DONE-запуск не переобъявляет изменившийся рабочий каталог проверенным.

Очередь использует lease, heartbeat, token каждого получения, ACK/NACK с проверкой владельца и дедупликацию публикации. `receive()` возвращает `(id, event, token)` без ACK. Доставка сообщений — at-least-once; exactly-once внешних действий не обещается. Ошибки generic-обработчиков сохраняются как failed; автоматической политики backoff пока нет.

Асинхронные провайдеры отменяются с завершением процесса; на POSIX завершается группа процессов. Generic синхронные обработчики исполняются в потоках: Python не может принудительно остановить произвольный поток, поэтому такие обработчики должны кооперативно останавливаться и не используются для production-вызова CLI агента.

## Память

```bash
python solar.py memory-search "калькулятор округление" --project default
python solar.py memory-stats
```

Память сохраняет содержательные выводы, evidence, агента, проект, task, run_id и источник. Повторная синхронизация одного запуска не дублирует записи. Записи провалившегося запуска не получают отметку проверенного результата.

Поиск использует индекс нормализованных слов в SQLite, фильтр проекта и точные совпадения токенов. Успешная QA даёт небольшой бонус только релевантным результатам. Это лексический поиск без embeddings, морфологии и семантического понимания. Отметка `qa_pass` связывает вывод с проверенным финальным запуском, но не доказывает каждое утверждение в тексте модели.

## Границы изоляции

Sun/Venera/Ceres/Mars/Moon/Mercury работают с копиями. Earth/Neptun изменяют основной каталог. Изменения содержимого проверяются хешами, даже без Git и для уже изменённых файлов. Несанкционированное изменение обнаруживается после факта; автоматического отката нет.

Это изоляция репозиториев, не контейнер или OS sandbox. Терминальные команды, установленный CLI и файлы проекта должны быть доверенными. Переменные окружения наследуются провайдером. MCP-права ограничивают только MCP-сервер, не собственные инструменты CLI. Символические ссылки не копируются. Для Git worktree с `.git`-файлом Git-инспекция в копии недоступна; используйте обычный checkout.

## MCP

См. `system/mcp/README.md`. Исправлен стандартный JSON-lines stdio, добавлены ролевые ограничения и запрет обхода пути через symlink. По умолчанию доступен Reader. Терминал выключен до явного локального разрешения. `git.commit` через MCP отключён; используйте `finalize`.

## Переход с 1.6

1. Сохраните резервную копию каталога и обеих SQLite-баз при остановленном Galaxy.
2. Используйте этот архив как отдельную версию; исходный архив не изменён.
3. Если обновляете собственную рабочую копию, переносите исходники, тесты и документацию; не перезаписывайте свои `tasks`, `memory`, `traces`, заметки и секреты данными из примера.
4. Схемы SQLite расширяются автоматически. Старые события без run_id остаются историческими и не исполняются новым маршрутом. Старые QA-отметки памяти сбрасываются, поскольку раньше означали только заявление модели.
5. Старые `agent-v1`-логи сохраняются, но не являются checkpoint для 1.7. Старый DONE требует свежей проверки. Уже запущенный 1.6-процесс перед обновлением остановите.

История прежних описаний — `docs/history-v0.5-v1.6.md`; актуальное поведение описывает этот README. Ограничения и список исправлений — `CHANGELOG.md`. Результаты проверок сборки — `TEST_RESULTS.json`.

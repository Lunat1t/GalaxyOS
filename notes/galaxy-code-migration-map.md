# Galaxy Code — инвентаризация и карта переноса

**Этап 0, шаг 3.** Снимок текущего устройства исходников для планирования миграции. Инвентаризация кода и путей; личные хранилища пользователя не открывались. В checkout каталога `data/` с данными сейчас нет.

## Что существует

| Данные сейчас | Путь и формат | Роль | План сохранения |
| --- | --- | --- | --- |
| Память и цели | `data/brain/index.db` — SQLite | BrainStore: записи, provenance, статусы, связи, revisions/audit; там же semantic embeddings, entity graph, goals и consolidation candidates | Скопировать целиком до запуска новой версии; сохранить ID и историю. Производные индексы можно перестроить только после сверки количества и контрольных выборок |
| Заметки vault | `data/vault/**/*.md` — обычные Markdown-файлы | Редактируемый источник заметок | Копировать дерево с путями и метаданными файлов; не переписывать текст при переносе |
| Индекс vault | `data/runtime/vault.db` — SQLite | Кэш заметок, ссылок и полнотекстового индекса | Не считать источником истины; после резервной копии можно пересоздать из Markdown и сравнить число заметок/ссылок |
| Опыт агентов | `data/runtime/experience/<project-hash>.sqlite3` — SQLite на корень репозитория | Эпизоды, доказательства, visibility, owner/team и поисковые термины | Сохранить все файлы. Для нового ID проекта вести явную таблицу старый hash → Project ID; не объединять проекты только по отображаемому имени |
| Профили и состояние агентов | `data/runtime/agents.db` — SQLite | Профили ролей, блоки памяти, опыт и состояние Moon/подагентов | Сохранить исходный файл. Переносить постоянные профили после ручного/правилового сопоставления; временные Moon и историю не превращать в постоянных Agent |
| Планы и выполнения | `data/runtime/autonomy.db` — SQLite; `data/runs/<id>/state.json` и логи — файлы | План DAG, узлы, попытки, approvals, метрики, снимки состояния и логи | Сохранить DB и каталоги запусков без преобразования как архив. Новые Run/Approval маппить отдельно; не считать старые approvals подтверждением нового diff |
| Проверки и правила | `data/runtime/verification.sqlite3` — SQLite | Проверки с хешами логов и предложенные/активные правила | Сохранить файл и ссылки на episodes. Кандидатные правила не повышать автоматически; проверить ID связанной истории |
| Интервью | `data/runtime/interviews.db` — SQLite | Сессии, ответы, DAG-вопросы и собранные Goal Brief | Сохранить историю целиком. Не преобразовывать сессии в Task без явного сопоставления; готовый Brief можно импортировать отдельно как пользовательский документ/цель |
| Экспорт планирования и brief | `data/planning/`, `data/briefs/` — JSON/Markdown | Трассы и пользовательские артефакты | Сохранять как файлы с исходными именами; при переносе добавлять ссылки на источник |
| Настройки и роли | `config/`, `galaxy_core/resources/` — JSON/Markdown в репозитории | Модельные профили, роли, интервью-шаблоны | Сохранить настройки. Отделить публичные настройки от секретов; секреты не копировать в память, конфигурацию проекта или журнал |

Пути runtime обычно строятся от `ROOT = Path(__file__).resolve().parent`, то есть каталога исходников Galaxy. Опыт отдельно вычисляет hash каталога репозитория для разделения одинаково названных проектов, но файл всё равно хранится под общим `ROOT/data`. Это надо заменить на пользовательский data root и каталог настроек при реализации Project; текущий inventory не переносит файлы.

CLI уже имеет команды `brain-*`, `goal-*`, `experience-*`, `agents`, `run/resume/status/logs/approve/reject`, `vault`, `migrate`, `interview-*` и `team-*`. Текущие runtime-механизмы можно использовать как источник форматов и поведения, но `agents.db`, `autonomy.db` и approvals ещё не соответствуют целевой схеме Project/Agent/Task/Run/Approval.

## Ограничение нынешнего мигратора

`galaxy_core/migration.py` копирует `memory/index.db` из старой сборки и выбранные папки Markdown (`daily`, `resources`, `projects`, `inbox`). Он не переносит нынешние `data/runtime/*.db`, каталоги `data/runs`, журналы, интервью и brief-файлы. Он выполняет копирование с пропуском существующих файлов, но не формирует полный отчёт сверки и отката. Поэтому его нельзя считать мигратором Galaxy v1 → Galaxy Code без расширения и проверки.

## Безопасный порядок миграции

1. Определить data root отдельно от установленного кода и создать новый Project registry; оригинальные папки оставить на месте.
2. Закрыть процессы Galaxy и сделать побайтовую резервную копию SQLite вместе с WAL/SHM и файловых данных. Записать пути, размеры, хеши файлов и время снимка.
3. Скопировать Markdown и оригинальные БД в staging-каталог; исходники не изменять. Для SQLite проверить целостность копии до чтения.
4. Создать явное отображение старых путей/hash/name/ID в новые `Project`, `Agent`, `Task`, `Run` IDs. Не угадывать связи при неоднозначности; оставить запись в legacy archive.
5. Импортировать сначала исходные данные памяти и профили с сохранением первичных ID, provenance, статусов и истории. Производные FTS/semantic/vault индексы пересоздать из источников отдельно.
6. Сверить по каждому источнику counts, уникальные ID, статусы, даты, ссылки и выборочные хеши/записи; сохранить машинно-читаемый manifest старое → новое с пропусками и причинами.
7. Открыть новую копию в read-only проверочном режиме, затем выполнить сценарии поиска, исправления, отзыва, vault sync и чтения истории Run. Не переключать активный data root до успешной сверки.
8. Переключение сделать обратимым: сохранить исходный root и manifest; при ошибке вернуть прежний root целиком. Удаление или очистка источника не входит в миграцию.

## Что ещё решить

Физический новый data root, точная схема Project registry, автоматическое сопоставление старых run/approval и сроки хранения архивов определяются после утверждения формата журнала событий на шаге 4 этапа 0. Эта карта описывает существующие пути и минимальные гарантии переноса, а не готовый код миграции.

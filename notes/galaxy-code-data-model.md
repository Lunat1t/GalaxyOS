# Galaxy Code — модель данных этапа 0

**Статус:** проект схемы, версия v1.0.2. Физическое хранилище и миграция пока не выбраны. Модель описывает целевые сущности, владельцев и жизненный цикл.

## Связи

```text
Project ──< AgentBinding >── Agent ──< Run >── Task
   │                           │          │
   └──────────────< Task >─────┘          ├──< Worker
                                         ├──< Event
                                         ├──< Verification
                                         ├──< Approval
                                         └──< MemoryRef

Agent ──< SkillBinding >── Skill
Agent/Project ──< ToolBinding >── Tool
Agent ── ProviderConfig ──> Provider
Run ── HarnessSnapshot ──> версии разрешений, инструментов и контекста
```

Связь Agent с Project задаётся через `AgentBinding`: профиль агента сохраняет устойчивый ID, а конкретный проект задаёт доступные ему навыки и разрешения. В первом срезе интерфейс может создавать одного агента по умолчанию, не меняя эту модель.

## Сущности и владелец данных

| Сущность | Что хранит | Кто владеет и меняет |
| --- | --- | --- |
| `Project` | Стабильный ID, путь к рабочей папке, настройки проекта, ссылку на репозиторий при наличии | Пользователь; путь можно обновить при переносе проекта, ID сохраняется |
| `Agent` | Стабильный ID, имя, образ, роль, инструкции, настройки провайдера, ссылку на долговременную память | Пользователь владеет профилем; Galaxy хранит историю работы со ссылками на Run |
| `AgentBinding` | Связь агента с проектом, разрешённые навыки и локальные настройки | Пользователь; связь не расширяет права сама по себе |
| `Task` | Запрос пользователя, проект, назначенный Agent, приоритет и состояние | Пользователь создаёт и может отменить; оркестратор меняет состояние выполнения |
| `Run` | Одна попытка выполнить Task: Agent, Provider, модель, начальные версии файлов, итог и причины остановки | Runtime создаёт append-only историю; повторный запуск создаёт новый Run |
| `Worker` | Временная подзадача, родительский Run, цель, ограниченные инструменты, результат | Оркестратор создаёт внутри Run; после завершения запись остаётся для аудита, профиль агента не создаётся |
| `Event` | Упорядоченное событие Run: запрос инструмента, ответ, вывод команды, статус, ошибка | Runtime только добавляет; исправления оформляются новыми событиями |
| `Verification` | Команда/проверка, статус, вывод и хеш состояния файлов, к которому относится результат | Проверяющий процесс создаёт; пользователь может запросить повторную проверку |
| `Approval` | Запрошенное действие, точный объект решения (например diff hash), решение, время и срок действия | Пользователь принимает решение; runtime применяет его только к совпадающему объекту |
| `Provider` | Тип адаптера и его возможности; секреты и локатор авторизации сюда не копируются | Galaxy хранит конфигурацию; учётными данными управляет пользовательская среда или защищённое хранилище |
| `Skill` / `Tool` | Описание и версия навыка или инструмента; Tool также описывает входы и побочные эффекты | Каталог Galaxy или пользователь; разрешение выдаётся отдельно |
| `HarnessSnapshot` | Снимок версий правил, разрешений, инструментов, окружения и выбранных источников контекста для Run | Runtime фиксирует при старте; запись не меняется после запуска |
| `MemoryRef` | Ссылка на существующую запись Brain/vault и причину включения в контекст | Brain/vault остаются владельцами содержимого; Run хранит только ссылку и факт использования |
| `Goal` / `Experience` | Существующие цели и эпизоды; у нового опыта есть ссылка на Run и доказательства | Существующие BrainStore/ExperienceStore; результат Run не становится подтверждённым знанием автоматически |

## Идентификаторы и границы

- Новые сущности получают устойчивые случайные ID, не зависящие от имени, пути, модели или провайдера. Имена и пути можно менять без потери ссылок.
- `Task` принадлежит одному `Project`; `Run` принадлежит одному `Task`; `Worker` — одному `Run`. Каждый `Event`, `Verification`, `Approval` и `MemoryRef` привязан к `Run`.
- Агент может использоваться в нескольких проектах только через явную `AgentBinding`. Доступ к памяти определяется её существующей областью видимости и политикой проекта; сам факт назначения Agent не открывает ему все записи.
- Конфигурация Provider не содержит API-ключей, токенов или секретов. Журнал не записывает секретные значения и не вкладывает их в промпт.
- Разрешения Worker — подмножество разрешений родительского Run. Worker не может запросить расширение прав или сам применить изменения.
- `Approval` относится к точному действию и неизменяемому содержимому: для diff — к хешу diff и базовой версии. Изменился diff или истёк срок — требуется новое решение.
- Содержимое существующих Brain-записей и Markdown-заметок не копируется в новые таблицы без необходимости; Run хранит provenance-ссылки.

## Жизненный цикл

```text
Project/Agent настроены
        ↓
Task создан → Run запущен → события / workers / проверки
                              ↓
                     diff и запрос Approval
                       ↙             ↘
                  отказ/отмена       подтверждение
                       ↘             ↙
                   Run завершён с результатом
                              ↓
                 Experience-кандидат с источниками
```

- Состояния `Task`: `queued → running → completed | failed | cancelled`.
- Состояния `Run`: `starting → running → awaiting_approval → completed | failed | cancelled | rejected`.
- Состояния `Approval`: `pending → approved | rejected | expired`. Решение не редактируется; новое решение получает отдельную запись.
- Завершённые `Run` и их события сохраняются. Повторное выполнение, продолжение после сбоя и исправление памяти оставляют видимую историю.
- Удаление Project или Agent не должно каскадно стирать Run, решения и происхождение памяти. Правило удаления профиля и срока хранения истории требует отдельного решения при проектировании хранилища.

## Что ещё предстоит решить

Этот логический контракт не выбирает SQLite-схему, сериализацию, транзакционные границы, индексирование или политику хранения журналов. Их определим после инвентаризации текущих хранилищ и проверок в следующем шаге этапа 0. Legacy-механизмы повторно используем только после проверки соответствия этим правилам.

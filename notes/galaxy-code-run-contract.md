# Galaxy Code — первый сценарий и журнал запусков

**Этап 0, шаг 4.** Контракт для первого локального среза: один Project, один постоянный Agent, Codex CLI, Run в ограниченном рабочем месте, проверки, diff и решение пользователя.

## Сценарий

1. Пользователь открывает каталог проекта. Galaxy показывает путь, Git-ветку и доступного Agent; при первом открытии создаёт запись Project с устойчивым ID.
2. Пользователь вводит задачу. Galaxy создаёт `Task`, показывает исполнителя и запускает новый `Run` с отдельной копией рабочего каталога.
3. Agent выполняет работу через Codex CLI. Galaxy показывает сообщения и этапы работы; инструменты и команды исполняются только с разрешёнными правами.
4. Galaxy запускает согласованные проектом проверки и привязывает их к хешу состояния файлов. Ошибка или отмена останавливает цикл и оставляет журнал.
5. Galaxy показывает diff, базовую Git-версию, список файлов и результат проверок. Для изменения исходного проекта запрашивается `Approval`, привязанный к хешу diff и базе.
6. При отказе изменения не применяются. При подтверждении Galaxy применяет только показанный diff и повторно проверяет состояние. Несовпадение хеша требует нового подтверждения.
7. Run завершается; Galaxy предлагает записать результат как Experience-кандидат со ссылками на Run и проверки. Запись памяти не подтверждается автоматически.

Если Codex CLI недоступен или Run прерван, Galaxy сообщает причину и сохраняет состояние для просмотра. Повторный запуск создаёт новый `Run`, связанный с тем же `Task` или его продолжением.

## Событие журнала

Каждое событие — неизменяемая запись с полями:

| Поле | Назначение |
| --- | --- |
| `event_id` | Уникальный ID события |
| `schema_version` | Версия формата события |
| `project_id`, `task_id`, `run_id` | Владельцы и связь с текущей работой |
| `sequence` | Возрастающий номер внутри Run для восстановления порядка |
| `occurred_at` | Время UTC |
| `actor_type`, `actor_id` | Пользователь, Agent, Worker, Provider или системный компонент |
| `event_type` | Тип события из перечня ниже |
| `payload` | Типизированные данные события; секреты запрещены |

### Обязательные типы первого среза

`task.created`, `run.started`, `provider.started`, `provider.message`, `tool.requested`, `tool.denied`, `tool.completed`, `verification.completed`, `diff.created`, `approval.requested`, `approval.decided`, `change.applied`, `run.completed`, `run.failed`, `run.cancelled`.

Для `diff.created` хранятся базовый commit или хеш исходного состояния, хеш diff и пути изменённых файлов. `verification.completed` хранит команду, exit code, краткий вывод и хеш состояния, на котором проверка запускалась. `approval.decided` хранит решение, время и точный хеш действия. Полные секретные значения, токены и переменные окружения в payload не записываются.

## Правила журнала

- События только добавляются; исправление или повторное решение создаёт новое событие.
- Порядок определяется `sequence`, а не часами. Повторная доставка от адаптера отсекается по `event_id` или idempotency key.
- Текущее состояние `Task` и `Run` — восстанавливаемая проекция событий, а не независимая история.
- Неполный Run после сбоя остаётся видимым; при восстановлении создаётся событие возобновления, а не переписываются старые.
- Вывод модели и инструмента хранится с ограничением объёма и редактированием секретов. Политика сроков хранения и очистки уточняется перед реализацией.

## Готовность этапа 0

Этап 0 считается описанным, когда приняты границы продукта, логическая модель, карта текущих данных и переноса, этот сценарий и формат событий. Реализация начинается с этапа 1: Project и основной TUI.

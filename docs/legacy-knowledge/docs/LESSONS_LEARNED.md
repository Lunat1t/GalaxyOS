# Lessons Learned — что не повторять в новой Galaxy

Этот документ фиксирует основные уроки старой реализации.

## 1. Не начинать с огромной архитектуры

Система слишком рано объединила orchestration, восемь статичных агентов, память, Obsidian/UI, MCP, WorkerMesh, sandbox-политику, Git-flow, задачи, world model и другие подсистемы. Архитектура росла быстрее доказательств её пользы.

**Правило:** новая подсистема появляется только для измеримого bottleneck.

## 2. Не строить ещё одного coding-agent

Наиболее сильное направление Galaxy — интеллектуальный слой контекста и памяти вокруг Codex/Claude/другого исполнителя. Galaxy должна улучшать то, что исполнитель знает до действия и что система сохраняет после действия, а не дублировать его способности.

## 3. Benchmark first

Перед сложным retrieval нужен одинаковый набор задач и baseline:
- naive/full-context;
- lexical retrieval;
- semantic retrieval;
- hybrid/attention.

Измерять Recall/Precision релевантных файлов, latency, размер context package/токены, стоимость и конечный solve rate.

## 4. Microbenchmark не равен продуктовой пользе

23 мс против 122 мс и 20,8 мс против 100,7 мс показывали ускорение отдельных компонентов. Они не доказывают, что агент решает больше задач, делает меньше ошибок или экономит стоимость end-to-end.

Три SWE-bench задачи — недостаточная выборка.

## 5. Контекст обязан иметь provenance

Для каждого знания должны быть понятны источник, время, project/user scope, надёжность и возможность проверить evidence. Более свежее подтверждённое знание должно иметь возможность отменить старое.

## 6. Память — не склад текста

Полезная идея: `event → episode → knowledge → skill/rule`. Но автоматическая консолидация должна требовать evidence. Ошибочное долговременное знание опаснее пропущенной заметки.

## 7. Факт, эксперимент и roadmap — разные вещи

Каждая возможность должна иметь явный статус: `implemented / experimental / planned / rejected`. Нельзя описывать roadmap так, будто функция уже существует.

## 8. Incremental updates и cache полезны

Локальные тесты показали заметное ускорение повторной сборки. Не нужно пересчитывать весь проект при небольшом изменении. Но сложность delta/event engine также должна оправдываться измерениями.

## 9. Multi-user scope проектируется сразу

Если Galaxy обслуживает команду, project/user/workspace scope и provenance должны быть частью модели данных с начала, иначе знания пользователей могут смешиваться.

## 10. Метафора не должна диктовать runtime

Sun, Earth, Mercury и другие роли были удобны для объяснения системы, но фиксированные персонажи не являются причиной существования отдельных агентов. Агент/роль нужен только когда он даёт измеримое преимущество.

## 11. Минимальное ядро следующей версии

Сначала доказать:
1. ingestion/indexing проекта;
2. retrieval нужного контекста;
3. компактный context package с provenance;
4. evaluation harness против baseline.

После этого рассматривать memory consolidation, entity graph, contradiction detection, team context, world model и agent orchestration.

## 12. Критерий успеха

Galaxy полезна, если на одинаковых задачах агент получает меньше мусора, быстрее получает нужные знания, реже пропускает релевантные файлы/решения, тратит меньше токенов/стоимости и/или чаще успешно завершает задачу.

Красота архитектуры сама по себе не является метрикой.

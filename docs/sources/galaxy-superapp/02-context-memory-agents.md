# Источники 0.2: контекст, поиск и оценка coding-агентов

Цель карточки — собрать только материалы, которые помогают решить конкретные вопросы Galaxy: что передавать модели, как искать проектные сведения, как проверять качество и когда усложнять агентный workflow.

## Оставить в основе

### 1. Контекст нужно подбирать и обновлять

Anthropic, [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), 2025.

**Что источник даёт:** описывает контекст как меняющееся состояние из инструкций, инструментов, внешних данных и истории. Его нужно каждый раз отбирать под текущую задачу и ограниченный бюджет; длинный контекст не гарантирует, что модель извлечёт нужное.

**Что взять для Galaxy:** проверять не только размер пакета, но полезность и свежесть включённых сведений; показывать источники и причину отбора. Это гипотеза для Galaxy, не доказательство, что его конкретный retrieval улучшает результат.

**Ограничение:** статья — практический материал Anthropic, а не независимая сравнительная оценка всех моделей. Отдельные объяснения о механике контекста не следует превращать в точный количественный закон без проверки.

### 2. Сравнивать retrieval на задаче, а не переносить чужие цифры

Anthropic, [Introducing Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval), 2024.

**Что источник даёт:** объясняет, почему лексический поиск полезен для точных идентификаторов и терминов, а embeddings — для сходства по смыслу; описывает их комбинацию и reranking.

**Что взять для Galaxy:** сравнить lexical, vector и hybrid режимы на одинаковых репозиториях, запросах и ограничениях. Отдельно проверять точность фрагмента, его связь с исходным документом и влияние на итоговую задачу.

**Ограничение:** проценты улучшения в публикации получены на данных и конфигурации Anthropic. Это не прогноз для Galaxy и не основание внедрять любой дополнительный retrieval-слой без собственного эксперимента. Источник также отмечает, что для небольшого корпуса может быть проще передавать весь корпус, если он помещается и это работает качественно; retrieval не нужен автоматически каждому проекту.

### 3. Агент оценивается по проверенному результату и следам запуска

Anthropic, [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), 2026.

**Что источник даёт:** различает задачу с критериями успеха, повторные попытки, grader, полный trace и фактическое состояние после запуска. Для стохастического агента одной попытки мало; проверки должны соответствовать тому, что действительно важно пользователю.

**Что взять для Galaxy:** фиксировать задачу, версию репозитория, модель, инструкции, контекст, инструменты, бюджет, несколько попыток и независимые проверки результата. Не считать финальное заявление агента подтверждением успеха.

**Ограничение:** это методический материал поставщика, основанный на его практике. В Galaxy нужно отдельно проверить стоимость повторных попыток, качество grader-ов и приватность сохраняемых traces. Trace может содержать чувствительные данные — сохранять только необходимое.

OpenAI: [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/) и [почему OpenAI перестала использовать Verified для оценки frontier-моделей](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/), 2024–2026.

**Что источник даёт:** история benchmark-а показывает, что human-validated набор всё равно может иметь проблемы тестов и загрязнения обучающими данными; один публичный score не равен устойчивой оценке способности.

**Что взять для Galaxy:** сочетать публичные наборы с собственными зафиксированными задачами и пилотами, указывать ограничения набора и проверять конечный результат.

**Ограничение:** это аргумент об оценке моделей на SWE-bench Verified, а не оценка retrieval или продукта Galaxy. Не делать вывод, что все benchmark-и бесполезны; проверять конкретную валидность каждого.

## Использовать как архитектурный ориентир, не как обязательное решение

### 4. Начинать с простого workflow, усложнять по результатам

Anthropic, [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), 2024.

**Что источник даёт:** различает предопределённые workflows и более автономных агентов. Рекомендует начинать с простого варианта и учитывать компромисс между качеством, задержкой и стоимостью.

**Что взять для Galaxy:** сначала проверить один прямой coding workflow и фиксированные роли; добавлять динамический выбор шагов или нескольких агентов только если измерения показывают выигрыш.

**Ограничение:** статья сама предупреждает, что описание инструментов 2024 года устарело. Использовать её для общего принципа простоты, но не для выбора актуального SDK или фреймворка.

### 5. MCP — протокол подключения, не готовая безопасность продукта

Model Context Protocol, [архитектура](https://modelcontextprotocol.io/docs/concepts/architecture), [спецификация 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25) и [Security Best Practices для этой версии](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).

**Что источник даёт:** MCP описывает роли host/client/server и способы передавать ресурсы, prompts и tools. Спецификация и security guidance отдельно подчёркивают согласие пользователя, контроль действий и необходимость защищать доступ к данным и инструментам.

**Что взять для Galaxy:** использовать MCP там, где он реально упрощает подключение к coding-клиентам; отдельно проектировать минимальные права, согласие, аудит, отмену действия и границу доверия для каждого инструмента.

**Ограничение:** поддержка протокола сама по себе не доказывает безопасность интеграции и не задаёт продуктовую авторизацию Galaxy. Спецификацию и security guidance нужно сверять с версией, поддерживаемой целевым клиентом.

## Проверять только при работе с API-кэшированием

### 6. Prompt caching зависит от провайдера и повторяемого префикса

- OpenAI, [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).
- Anthropic, [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Официальная документация нужна как техническая справка для конкретных API: условия попадания в кэш, поддерживаемые параметры и биллинг меняются. Она **не нужна как отдельное продуктовое основание** для roadmap и не подтверждает, что Galaxy сэкономит деньги.

Если Galaxy вызывает API напрямую, измерять cached/uncached tokens, стоимость и задержку по каждой модели и проверять инвалидирование при изменении файлов или инструкций. Если Galaxy только передаёт контекст внешнему клиенту, кэш может контролироваться этим клиентом и быть вне управления Galaxy.

## Критический итог для roadmap

Из этой карточки реально следуют четыре направления для проверки:

1. Подбирать контекст под задачу и показывать его происхождение.
2. Сравнивать способы поиска на одинаковых coding-задачах и измерять влияние на конечный результат.
3. Оценивать агентные запуски по критериям, фактическим проверкам, нескольким попыткам и безопасно обработанным traces.
4. Сохранять простую оркестрацию, пока дополнительная сложность не доказала пользу.

Не следует выводить из этих источников обязательность графовой базы, отдельного memory engine, динамических агентов, нового framework или конкретного UI. Для таких решений потребуются данные реальных пользователей и собственные эксперименты Galaxy.

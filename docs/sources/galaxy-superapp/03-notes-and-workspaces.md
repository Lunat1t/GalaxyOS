# Источники 0.3: заметки и организация проекта

Эта карточка проверяет две отдельные гипотезы: нужны ли разработчику заметки, связанные с кодом, и нужно ли объединять заметки с задачами проекта. Сами по себе существующие продукты этого не доказывают.

## 1. Obsidian: Markdown-файлы и связи

Официальная справка:
- [Как Obsidian хранит данные](https://obsidian.md/help/Files%2Band%2Bfolders/How%2BObsidian%2Bstores%2Bdata).
- [Ссылки между заметками](https://obsidian.md/help/link-notes).

### Что подтверждает материал

- заметки Obsidian — обычные Markdown-файлы в локальной папке; их можно менять внешним редактором;
- заметки можно связывать, переходить по ссылкам и смотреть обратные ссылки;
- Obsidian поддерживает локальный кэш метаданных, который может устареть и потребовать перестроения.

### Что это даёт Galaxy

Это основание рассматривать Markdown как переносимый формат заметок и проверять простой сценарий: разработчик сохраняет решение в файле, а Galaxy находит его по запросу и показывает связь с исходником или задачей.

### Чего источник не доказывает

Он не доказывает, что разработчикам нужен отдельный редактор Galaxy, графический граф, Obsidian-совместимость или собственная система синхронизации. Описание возможностей Obsidian — не исследование спроса на Galaxy.

**Оценка:** полезен для формата файлов и нескольких UX-паттернов; не использовать как спецификацию продукта.

## 2. GitHub Projects: задачи рядом с репозиторием

GitHub Docs:
- [Что такое Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects).
- [Рекомендации по Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/best-practices-for-projects).

### Что подтверждает материал

GitHub Projects строит представления поверх issues и pull requests: таблицу, доску или timeline, добавляет поля и фильтры, связывает элементы с кодом и обновляет представления при изменении задач и PR.

### Что это даёт Galaxy

Полезный паттерн здесь — не «сделать свой GitHub Projects», а не дублировать внешний трекер без нужды. Если Galaxy покажет задачи в комнате, следует выяснить, достаточно ли ссылок и чтения из GitHub, или людям действительно нужен ещё один источник правды.

### Чего источник не доказывает

Документация описывает продукт GitHub и его функции. Она не доказывает, что Galaxy должен хранить backlog, синхронизировать статусы, делать канбан или заменять issues/PR.

**Оценка:** слабый продуктовый ориентир. Использовать только для проверки интеграционного сценария с GitHub, не как основание добавлять собственный task manager.

## Важное разделение сценариев

«Заметки проекта» и «управление задачами» — разные нужды:

- заметка хранит объяснение, решение, план или найденный контекст;
- issue/PR фиксирует работу, состояние и обсуждение в трекере;
- запуск агента сохраняет задачу, действия и результаты проверок.

Galaxy не должен объединять их в одну сущность без пользовательского сценария. Для начала достаточно ссылать эти материалы друг на друга и сохранять происхождение.

## Как проверить потребность без большого UI

1. Найти у нескольких разработчиков реальные недавние случаи, когда они повторно искали принятое решение или объясняли его агенту.
2. Для этих задач использовать существующие Markdown-файлы или простую папку заметок рядом с репозиторием.
3. Проверить, может ли текущий Galaxy найти нужную заметку и показать путь/фрагмент с источником.
4. Отдельно проверить, хватает ли ссылки на GitHub issue/PR или пользователи просят синхронизируемое представление задач.
5. Сравнить время до нужного решения, пропущенные источники, нерелевантные находки и ручные исправления.

Не строить редактор, визуальный граф, канбан или облачную синхронизацию, пока этот тест не выявит конкретное ограничение.

## Вывод для roadmap

Пока источник оправдывает только проверку совместимости с Markdown и простого поиска заметок проекта. Он не оправдывает переход к комнате как большому интерфейсу и не доказывает необходимость второго менеджера задач.

В долгосрочном плане следующий шаг должен остаться вопросом для проверки: **помогает ли связь «репозиторий + Markdown-решения + ссылки на issue/PR» разработчику быстрее продолжить работу?**
